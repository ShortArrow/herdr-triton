# 0012. リスナーは常駐し、待つものが無い間は静かにする

[English](../../adr/0012-resident-listener-quiet-when-idle.md) | 日本語

- Status: Accepted
- Base: [`53063f0`](https://github.com/ShortArrow/herdr-triton/commit/53063f029d0e14e019ac27c4d803a87e51d2898b)

## Context

`trident` はシリアルポートを持ち、キーイベントを読み、herdr とやりとりする。そのため、キーが意味を持つ間は何かが動いている必要があり、Jump の最後の段（ADR 0011）はいつでも意味を持つ。
herdr のプラグインは v1 では常駐するデーモンではなく、startup とイベントのフックが呼び出しごとにプロセスを起動する。
herdr はフックのプロセスも、そこから起動したプロセスも、時間切れで止めたり終了させたりしない。ただしプラグインのドキュメントは、今後もそうだとは約束していない。
herdr は `pane.agent_status_changed` のフックをすべての pane について実行する（herdr `0d5d6f1`、`src/app/api/plugins/runtime.rs`、`PLUGIN_HOOK_EVENT_KINDS`）。
ホストが聞いていない間、ファームウェアはキーの押下を捨てる（`NoHost`）ので、押下があとで再生されることは無い。

プロセスを動かし続けることの代償を、Windows 11 と herdr 0.9.1 で計測・再現した。

- 待つものが無い間も herdr を 250 ms ごとにポーリングするのは、誰も必要としない仕事である。Jump に herdr の状態が要るのは、押した瞬間だけ
- フックが起動した子プロセスは、フックの標準出力と標準エラーを引き継ぐ。これは herdr のパイプなので、herdr は子プロセスが終わるまでフックを実行中と数える（再現済み: 出力の終わりが 23 ms でなく、子プロセスの 6 秒後に届いた）。herdr が同時に実行できるプラグインのコマンドは 32 まで
- 何もしない Rust のループでも、Private Bytes は 0.9 MB 近くから始まり、10 分で約 1.2 MB まで増える。`interprocess` で約 300 KB、シリアルポートの列挙で約 260 KB（SetupAPI が読み込まれたまま残る）、`serde_json::Value` を経由した `agent.list` の解析で約 350 KB 増える
- デバイスのエラーで終了するプロセスは、次にエージェントのステータスが変わるまでキーパッドを使えなくする。スリープからの復帰などで起きる
- herdr は名前付きセッションを例外的なものとして扱う。「Use workspaces first」（herdr のドキュメント concepts）

## Decision

- プラグインは、`startup` と `pane.agent_status_changed` で `trident hook` を実行する。
  herdr が `HERDR_SOCKET_PATH` を渡すので、リスナーは自分を起動したセッションを受け持つ（ADR 0007）
- `trident hook` は短命にする。
  リスナーが名前付きミューテックスを持っていれば、リスナーの起床イベントを発行して終了する。
  持っていなければキーパッドのポートを探し、`trident listen --port <COM>` を起動して終了する。
  起動の前に自分の標準ハンドルの継承フラグを外し、子プロセスはコンソールから切り離し、新しいプロセスグループにして、作業ディレクトリをプラグインの状態ディレクトリ（`HERDR_PLUGIN_STATE_DIR`）に置く。ログはそこの `trident.log` に書く
- `trident listen` は、受け持つ herdr サーバーが動いている間ずっと常駐する。
  名前付きミューテックスを持ち、静かな状態か動いている状態のどちらかにいる。
  - 静か（承認待ちも `done` も無い間）: herdr には何も問い合わせない。`KEY:EVENt?` は 250 ms ごと。LED は、まだ働くただ1つのキーである Jump だけを白で呼吸させる。1 秒ごとに、接続せずに herdr のエンドポイントがまだあることを確かめる（Windows では `WaitNamedPipeW`）。これで、問い合わせなくても herdr が止まったことに気付ける。起床イベントかキーの押下で動いている状態になり、キーを処理する前に `ping` を送ってスナップショットを取る
  - 動いている: ADR 0004 と ADR 0011 のループ。`KEY:EVENt?` は 20 ms ごと。承認待ちも `done` も無くなって 5 秒で静かな状態に戻る
- リスナーは、herdr に 5 秒続けて届かないかエンドポイントが無いとき、herdr のバージョンが対応外のとき、`trident stop` のときに終了する。
  herdr への呼び出しには、すべてタイムアウトを付ける。
  デバイスのエラーでは終了せず、短命な `trident find-port` で 1 秒ごとにキーパッドを探し直す。これで SetupAPI がリスナーに読み込まれない
- リスナーを最初に起動したセッションがキーパッドを使い続ける。セッション間での受け渡しはしない
- メモリの目標は、タスクマネージャーの「メモリ」列で 1 MB 以下とし、1 時間動かした間の最大値で判定する。
  そのため、リスナーは C ランタイムを静的にリンクし、`interprocess` の代わりに `std` の named pipe（使用中なら待つ）を使い、herdr の応答を `Value` を経由せず型に直接読み込む
- `trident run` は、プラグインを使わないときのために、静かな状態も終了の規則も持たない動いている状態のループを前面で回す

## Consequences

- herdr が動いている間は、最後の段を含めていつでも Jump が使える
- 待つものが無い間、herdr への問い合わせは無く、キーパッドへの問い合わせは 1 秒に4回になる
- シリアルポートの排他と名前付きミューテックスで、リスナーはユーザーセッションごとに1つになる
- Windows では実行中のファイルを置き換えられないので、プラグインを作り直す前に `trident stop` が要る
- シリアルターミナルからキーパッドを使うには、先に `trident stop` が要る
- 待つものが無い間は Jump の LED だけが白で呼吸するので、3つとも薄い白（`NoHost`）なら、リスナーがいない。herdr が動いていないか、`trident` が失敗している
- キーをまたいで流れる虹色（`WAVe`）は、LED の動作確認用にだけある
- ここで使う仕組み（名前付きミューテックスとイベント、切り離した起動、ハンドルの継承）は Windows のもの。Linux と macOS に対応するには、それぞれの代わりが要る

## Alternatives

- **フックごとにリスナーを起動し、待つものが無くなって 5 秒で終了させる**: 待つものが無い間は何も動かないが、長く放置したあとの Jump は効かず、ADR 0011 の最後の段にも届かない
- **常駐して herdr を 250 ms ごとにポーリングし続ける**: 単純だが、何もしない間に 1 日 345,600 回 herdr に接続する
- **ログオン時に `trident run` を起動する**: herdr が動いていない間も動き、OS の自動起動の設定が要る
- **`[[startup]]` から切り離さずに常駐プロセスを起動する**: herdr はプロセスが動いている間ずっとフックを実行中と数え、同時に実行できるプラグインのコマンド 32 の枠を使い続ける
- **一度きりのフックとし、デバイスを herdr で割り当てた HID キーボードにする**: リスナーが要らなくなるが、キー入力はフォーカスのあるウィンドウに入り、デバイスは単なる IO 機器でなくなる（ADR 0001）
- **待つものが無いときに別のセッションへキーパッドを譲る**: herdr の方針では複数セッションは珍しく、受け渡しには専用の仕組みが要る
