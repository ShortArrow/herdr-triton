# 0012. リスナーは常駐し、待つものが無い間は静かにする

[English](../../adr/0012-resident-listener-quiet-when-idle.md) | 日本語

- Status: Accepted
- Base: [`d76a26c`](https://github.com/ShortArrow/herdr-triton/commit/d76a26c18999f62d63dba53f320421c6af3c3d08)
- Supersedes: 0008
- Amends: 0009（LED の動作確認用の `WAVe` モード、プロトコル 3）、0011（最後の段をいつでも使えるようにする）

## Context

ADR 0011 の最後の段（全エージェントを巡回する Jump）は、リスナーが動いている間しか使えない。
一方 ADR 0008 のリスナーは、待つものが無くなって 5 秒で終了する。
リスナーを動かし続けることの代償を、Windows 11 と herdr 0.9.1 で計測・再現した。

- 待つものが無い間も herdr を 250 ms ごとにポーリングするのは、誰も必要としない仕事である。Jump に herdr の状態が要るのは、押した瞬間だけ
- フックが起動した子プロセスは、フックの標準出力と標準エラーを引き継ぐ。これは herdr のパイプなので、herdr は子プロセスが終わるまでフックを実行中と数える（再現済み: 出力の終わりが 23 ms でなく、子プロセスの 6 秒後に届いた）。herdr が同時に実行できるプラグインのコマンドは 32 まで
- 今のリスナーは、タスクマネージャーの「メモリ」列で 1.2 MB。この PC では、何もしない Rust のループでも Private Bytes は 0.9 MB 近くから始まり、10 分で約 1.2 MB まで増える。`interprocess` で約 300 KB、シリアルポートの列挙で約 260 KB（SetupAPI が読み込まれたまま残る）、`serde_json::Value` を経由した `agent.list` の解析で約 350 KB 増える
- デバイスのエラーで終了するリスナーは、次にエージェントのステータスが変わるまでキーパッドを使えなくする。スリープからの復帰などで起きる
- herdr は名前付きセッションを例外的なものとして扱う。「Use workspaces first」（herdr のドキュメント concepts）

## Decision

- `bridge hook` は短命にする。
  リスナーが名前付きミューテックスを持っていれば、リスナーの起床イベントを発行して終了する。
  持っていなければキーパッドのポートを探し、`bridge listen --port <COM>` を起動して終了する。
  起動の前に自分の標準ハンドルの継承フラグを外し、子プロセスはコンソールから切り離し、新しいプロセスグループにして、作業ディレクトリをプラグインの外に置く
- `bridge listen` は、受け持つ herdr サーバーが動いている間ずっと常駐する。
  名前付きミューテックスを持ち、静かな状態か動いている状態のどちらかにいる。
  - 静か（承認待ちも `done` も無い間）: herdr には何も問い合わせない。`KEY:EVENt?` は 250 ms ごと。LED は、まだ働くただ1つのキーである Jump だけを白で呼吸させる。1 秒ごとに、接続せずに herdr のエンドポイントがまだあることを確かめる（Windows では `WaitNamedPipeW`）。これで、問い合わせなくても herdr が止まったことに気付ける。起床イベントかキーの押下で動いている状態になり、キーを処理する前に `ping` を送ってスナップショットを取る
  - 動いている: ADR 0004 と ADR 0011 のループ。承認待ちも `done` も無くなって 5 秒で静かな状態に戻る
- リスナーは、herdr に 5 秒続けて届かないかエンドポイントが無いとき、herdr のバージョンが対応外のとき、`bridge stop` のときに終了する。
  herdr への呼び出しには、すべてタイムアウトを付ける。
  デバイスのエラーでは終了せず、短命な `bridge find-port` で 1 秒ごとにキーパッドを探し直す。これで SetupAPI がリスナーに読み込まれない
- リスナーを最初に起動したセッションがキーパッドを使い続ける。セッション間での受け渡しはしない
- メモリの目標は、タスクマネージャーの「メモリ」列で 1 MB 以下とし、1 時間動かした間の最大値で判定する。
  そのため、リスナーは C ランタイムを静的にリンクし、`interprocess` の代わりに `std` の named pipe（使用中なら待つ）を使い、herdr の応答を `Value` を経由せず型に直接読み込む

## Consequences

- herdr が動いている間は、最後の段を含めていつでも Jump が使える
- 待つものが無い間、herdr への問い合わせは無く、キーパッドへの問い合わせは 1 秒に4回になる
- Windows では実行中のファイルを置き換えられないので、プラグインを作り直す前に `bridge stop` が要る
- シリアルターミナルからキーパッドを使うには、先に `bridge stop` が要る
- 待つものが無い間の LED は、3つとも薄い白（`NoHost`）ではなく、Jump だけの白の呼吸になる。薄い白は、リスナーがいないこと（herdr が動いていないか、bridge が失敗した）を表すようになる
- キーをまたいで流れる虹色（`WAVe`）を待機中の表示として試したが、LED の動作確認用にだけ残した
- ここで使う仕組み（名前付きミューテックスとイベント、切り離した起動、ハンドルの継承）は Windows のもの。Linux と macOS に対応するには、それぞれの代わりが要る

## Alternatives

- **ADR 0008 のまま終了までの時間を延ばす**: プロセスの作りは変わらないが、長く放置したあとの Jump は効かない
- **常駐して herdr を 250 ms ごとにポーリングし続ける**: 単純だが、何もしない間に 1 日 345,600 回 herdr に接続する
- **ログオン時に `bridge run` を起動する**: herdr が動いていない間も動き、OS の自動起動の設定が要る
- **待つものが無いときに別のセッションへキーパッドを譲る**: herdr の方針では複数セッションは珍しく、受け渡しには専用の仕組みが要る
