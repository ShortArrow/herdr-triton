# 0009. CDC-ACM 上で SCPI 風のテキストを使う

[English](../../adr/0009-scpi-text-protocol.md) | 日本語

- Status: Accepted
- Base: [`53063f0`](https://github.com/ShortArrow/herdr-triton/commit/53063f029d0e14e019ac27c4d803a87e51d2898b)

## Context

デバイスは単なる IO 機器であり（ADR 0001）、この種の機器はシリアルターミナルから SCPI で操作するのが一般的である。
このリポジトリのデコーダでしか読めない形式では、デバイスを確かめるだけのために、そのツールをビルドして動かすことになる。
`firmware` と `trident` はどちらも Rust で、`no_std` でビルドできる `protocol` を通じてメッセージの型を共有する。両端が型付きの定義を持てば、食い違いはコンパイル時に分かる。
通信路はバイト列なので、途中から読み始めた側や壊れたメッセージに出会った側は、次の区切りを自分で見つける必要がある。

## Decision

通信路は USB CDC-ACM とする。
ホストは SCPI 風のコマンドをテキストの行で送り、デバイスは問い合わせにだけ答える。
キーイベントはデバイスのキューに溜め、`KEY:EVENt?` で読み出す。
`protocol` crate は型付きのコマンドと返事をそのテキスト表現とともに持ち、両端は1つの定義を共有する。

## Consequences

- どのシリアルターミナルからでも、このリポジトリのツールなしで、デバイスの識別、LED の設定、キーの読み出しができる
- デバイスは自分から何も送らないので、ターミナルには打ったコマンドへの返事だけが表示される
- どのメッセージも改行で終わるので、読む側は次の行で同期し直せる
- キーイベントは送られてくるのではなく、ポーリングで取りに行く。このポーリングがホストの生存通知も兼ねる
- firmware に小さなパーサとフォーマッタが載る。これは `protocol` を通じてホスト上でテストする

## Alternatives

- **postcard のメッセージを COBS で区切り `0x00` で終える**: コンパクトで、メッセージの型を両端でそのまま使えるが、シリアルターミナルからは中身が読めず、デバイスを確かめるにはこのリポジトリ独自のデコーダが要る
- **キーイベントを、問い合わせ無しに行として送る**: 遅延は小さいが、返事と混ざり、SCPI 機器の振る舞いとも違う
- **CDC-NCM と UDP**: ホストでシリアルポートを探さずに済み、WSL 2 のミラーモードのネットワークなら usbipd なしでデバイスに届くかもしれない。RP2040 に TCP/IP スタック、アドレスの決め方、ホストに新しいネットワークアダプタとファイアウォールの規則が要り、`usb-device` 0.3 用の NCM クラスは存在しない。`embassy-usb` にはあるが、ADR 0002 で除いている。ホストがいることを示す DTR も使えなくなる。Windows には NCM のドライバ（`UsbNcm.sys`）はあるが、ECM のものは無い
